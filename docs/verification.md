# 검증 기록

## PR #16 리뷰 반영: 모서리를 스치는 직진에서 멈추는 문제 — 2026-10-26

리뷰 지적대로 반지름 23은 증상만 고친 것이었다. 몸 통과 판단(`BodyCanPass`)은 옆선을 반지름보다 0.5 좁게 긋고, 몸 이동(`MoveBody`·`CanOccupy`)은 반지름 전체로 막는다. 그래서 몸 중심선이 모서리를 반지름보다 0.5 미만으로 가깝게 스치면, 직진으로 판단해 모서리에 걸린다. 대원과 같은 줄이면 방향의 옆 성분이 0이라 미끄러지지도 못하고 멈춘다. 반지름 23은 칸 가운데 줄만 이 구간에서 뺐다.

재현:

- 한 칸 틈 맵에서 대원과 적을 모서리를 스치는 같은 줄에 세웠다. 반지름보다 0.1·0.25·0.4 가까운 줄이다. 병사·분쇄자·철위병 모두 모서리 앞에서 멈췄다.
- 스치는 거리를 0~1.2까지 0.01 간격으로 촘촘히 보면 1,452번 가운데 1,169번 멈췄다. 흐름장을 따라가다 이 구간으로 들어서면 다시 직진으로 판단되기 때문이다.
- 생성 맵 300개에서 대원을 캠프 가운데에서 가로·세로 60 안으로 비켜 세우고 세 종류 모두 쫓게 했다. 2,700번 가운데 9번(분쇄자 5, 철위병 4) 오지 못했다.

고친 것:

- 조향: 직진이 그 틱에 한 걸음의 절반도 가지 못하면 흐름장 방향으로 다시 구해 움직인다. `MoveBody`는 상태를 바꾸지 않는 계산이라 다시 구해도 된다.
  - 처음에는 전혀 못 갔을 때만 바꿨다. 그러면 모서리 앞에서 대원의 줄 쪽으로 틱마다 0.0012씩 미끄러지는 것도 나아간 것으로 쳐서, 직진과 흐름장을 오가며 벗어나지 못했다.
  - 벽에 45도로 부딪혀 미끄러지면 한 걸음의 0.7배쯤 가므로 그대로 직진한다.
  - 고친 뒤 촘촘한 스침 1,452번과 생성 맵 추적 2,700번이 모두 통과했다.
- 적 정의의 생성자가 몸 지름이 한 칸 이상인 정의를 거절한다. 반지름 24는 칸 가운데 줄의 여유가 0이라 흐름장을 따라가도 걸린다. 같은 정의에 반지름만 24로 둔 적은 고친 조향으로도 한 칸 틈 8곳 중 2곳만 지나갔다.
- 모든 적 종류(`EnemyDefinition.All`)와 가장 큰 몸(`LargestRadius`)을 한 곳에 두었다. 기록의 종류 되읽기, 증원 타원 검사, 검사들이 쓴다. 생성기의 처음 적 구성과 증원 종류는 정해 둔 구성이라 그대로다. 적이 행동을 고르는 거리 75는 `Match.EngageDistance`로 뺐다.

확인한 것:

  - `GrazingLine`: 세 종류가 틈 위아래 모서리를 반지름보다 0.1~1 가깝게 스치는 줄에서 출발해 모두 틈을 지난다.

## 철위병이 모서리와 한 칸 틈에 걸려 멈추던 문제 — 2026-10-25

생성 맵에서 철위병(반지름 24)이 장애물 모서리와 한 칸 틈 앞에서 멈췄다. 생성 작전에서 엘리트를 켠 PR #14부터 드러났다. 그 전 운영 방은 손으로 만든 맵에 병사만 나왔다.

원인: 철위병의 몸 지름이 한 칸(48)과 같았다. 이렇게 겹쳐 멈췄다.

- 흐름장은 칸 가운데를 가리키므로, 칸 가운데 줄을 따라가는 몸이 벽 모서리에 딱 붙는다(여유 0).
- 반올림으로 조금만 안쪽으로 들어가면 모서리에 걸린다.
- 몸 통과 판단(`BodyCanPass`)은 옆선을 반지름보다 0.5 좁게 그어 이 경우를 지나갈 수 있다고 보고 대원에게 직진시킨다.
- 대원과 같은 줄이면 방향의 옆 성분이 반올림으로 0이 되어, 벽을 따라 미끄러지지도 못한다.

틈 앞에서 멈춘 철위병의 좌표를 찍어 확인했다. 대원이 y = 312에 있을 때 철위병은 (478.24, 311.968)에서 멈췄다. 모서리(480, 288)를 지나려면 y가 312 이상이어야 하는데 312에 다가가기만 하고 넘지 못했다.

처음에는 생성기가 장애물 사이를 한 칸만 띄우는 것이 원인이라고 보고 통로를 두 칸으로 넓혀 봤다. 그래도 두 칸 틈에서 출발점 8곳 중 3곳은 멈췄다. 그래서 생성기는 그대로 두고 철위병의 반지름을 23으로 줄였다(시험 설정). 같은 정의에서 반지름만 바꿔 비교했다.

| 실험 | 반지름 24 | 반지름 23 |
| --- | --- | --- |
| 한 칸 틈, 출발점 8곳 | 2곳 통과 | 8곳 통과 |
| 두 칸 틈, 출발점 8곳 | 5곳 통과 | 8곳 통과 |
| 생성 맵 1,000개, 처음 자리 셋에서 캠프의 대원까지 | 202개 맵만 셋 모두 옴 | 1,000개 모두 옴 |

분쇄자(22)와 병사(13)는 처음부터 모두 지나갔다.

함께 고친 것: 화면 안내(FIELD NOTES)의 "첫 작전에는 1티어 적만 등장합니다"는 생성 작전에 엘리트가 나온 뒤로 틀린 말이었다. 이제 Ⅱ(대응 2)로 표시된 엘리트 행동은 유효한 대응이 둘 겹쳐야 파훼된다고 안내한다.

확인한 것:

- 서버 검사 125/125(세 번 거듭 돌림), 결정론 묶음 24/24.
  - `EncounterTests.NarrowGap`: 적 셋의 몸 지름이 한 칸보다 작고, 한 칸 틈을 출발점 일곱 곳에서 모두 지나간다.
  - `GeneratorTests.EnemiesReachCamp`: 생성 맵 50개에서 몸이 가장 큰 적이 처음 자리 셋에서 각각 캠프의 대원에게 온다. 결정론 묶음에도 들어 있어 Windows·macOS에서도 같은 이동인지 본다.
  - `LayoutTests.EnemyBodies`의 맞닿음 거리를 45로 고쳤다(분쇄자 22 + 철위병 23).
  - 클라이언트 예측 대조 자료를 다시 만들었다. 바뀐 것은 시나리오 하나의 철위병 몸 반지름뿐이다(대원의 이동 결과는 그대로).

## 방 수 상한을 맵 생성 전에 확인(PR #15) — 2026-10-23

PR #14에서 맵과 `Match`를 생성 잠금 밖에서 만들면서, 방 수 상한에 걸려 거절할 요청도 맵을 한 번 만들고 버리게 됐다(최악 약 17ms).

- 처음에는 맵을 만들기 전에 잠금 밖에서 상한을 한 번 보고, 잠금 안에서 다시 확인했다. 리뷰에서 이 확인이 맵을 만들고 있는 요청을 세지 않는다는 지적을 받았다. 방이 31개일 때 요청 20개가 함께 들어오면 모두 통과해 맵 20개를 만들고 19개를 버린다. 방 3개를 가진 주소가 요청 30개를 한꺼번에 보내도 같다.
- 그래서 자리를 예약하는 방식으로 바꿨다. 맵을 만들기 전에 생성 잠금 안에서 자리를 예약하고(`Reserve`), 상한은 등록된 방과 맵을 만들고 있는 방을 합쳐 센다(서버 전체 `_reserved`, 주소별 `_reservedByAddress`). 방을 등록하면 같은 잠금 안에서 예약을 풀고, 만들다 예외가 나면 `finally`에서 푼다. 서버 전체 상한은 상수 `RoomHost.MaxRooms`로 뺐다.
- 검사의 시드 함수가 내준 시드 수(`TestSeeds.Issued`)를 센다. RoomHost는 맵을 만들 때마다 시드를 하나 받으므로, 이 수로 거절한 요청이 맵을 만들지 않았는지 안다.

확인한 것:

- 서버 검사 123/123(다섯 번 거듭 돌림), 결정론 묶음 23/23.
  - `RoomsPerAddress`, `ServerFull`: 상한에 걸린 요청은 시드를 받지 않는다.
  - `PendingRooms`: 맵을 만들고 있는 동안 끼어든 요청이 상한을 넘지 않고 맵도 만들지 않는다. 시드 함수 안에서 같은 RoomHost로 방을 한 번 더 만들어, 맵을 만들고 있는 요청과 동시에 들어온 요청을 만든다. 주소별 상한과 서버 전체 상한을 모두 본다.
  - `FailedCreation`: 맵을 만들다 예외가 난 요청은 예약을 돌려놓아, 그 뒤에도 주소와 서버가 상한만큼 방을 만들 수 있다.
- 일부러 되돌려 검사가 잡는지 확인했다.

| 되돌린 것 | 실패한 검사 |
| --- | --- |
| 첫 방식(잠금 밖에서 미리 확인) | `PendingRooms` |
| 서버 전체 상한에서 예약을 세지 않음 | `PendingRooms` |
| 주소별 상한에서 예약을 세지 않음 | `PendingRooms` |
| 실패한 요청의 예약을 풀지 않음 | `FailedCreation` |

- 브라우저 검사 27/27. 남은 기록 10개를 `--strict`로 재생해 모두 재현했다.

## PR #14 리뷰 반영 — 2026-10-23

리뷰 7건을 모두 고쳤다.

- 처음 적 자리: 시설 둘이 가까우면 두 시설의 적이 같은 칸에 놓여 `Match` 생성자가 예외를 냈다(시드 5,000개 가운데 14개, 리뷰가 든 39·461·554·662 포함). 이제 처음 적과 들판 보급의 자리 칸은 비워 둔 칸(시설 울타리와 그 바깥 통로, 캠프·탈출 지점 둘레, 앞서 둔 자리의 둘레)이 아니어야 한다. 그래서 서로 같은 칸이나 이웃 칸에 놓이지 않고 울타리 안에도 놓이지 않는다.
- 들판 보급: 같은 규칙으로 시설 가운데·처음 적 칸·울타리 안에 놓이지 않는다. 고치기 전 시드 5,000개에서 시설 가운데와 겹친 보급 84개, 처음 적 칸과 겹친 보급 84개, 울타리 안의 보급 1,132개, 처음 적의 이웃 칸 보급 541개였다.
- 배치 검사: 처음 적 자리는 그 종류의 몸이 벽에 닿지 않고 들어가야 하고 두 적의 몸이 겹치지 않아야 한다. 그래서 검사를 통과한 배치로는 언제나 방을 만들 수 있다.
- 맵 크기: 배치를 다시 만들 때 크기도 다시 뽑는다. 크기마다 200번씩 만들어 보니 가장 어려운 34×26도 한 번에 약 19%만 실패해, 전에도 80번이 모두 실패할 일은 사실상 없었다. 그래도 크기를 다시 뽑으면 어려운 크기에 묶이지 않는다.
- 방 만들기: 맵 생성과 `Match`를 생성 잠금 밖에서 만든다. 잠금 안에서는 방 수 상한 확인과 방 등록만 하고, 방 코드가 겹치면 맵은 그대로 두고 코드만 다시 뽑는다. 생성 실패를 다른 시드로 다시 시도하는 처리는 넣지 않았다. 증상만 가리기 때문이다. 대신 생성기가 방을 만들 수 있는 배치만 내놓게 했다.
- 검사 시드: `RoomHost`가 시드를 만드는 함수를 받을 수 있다(`seeds`, 운영 서버는 넘기지 않는다). 검사의 `RoomHost`는 모두 `TestTools.NewHost`로 만들어 방마다 정수 1, 2, 3, …으로 만든 시드를 쓴다. 무작위 시드를 쓰던 `Room(code, address)` 생성자는 검사 하나만 쓰고 있어 지웠다. 재접속 검사(`Reconnect`)는 그 방의 캠프에 투입하고 투입 결과도 확인한다.

확인한 것:

- 고친 생성기로 시드 100,000개를 만들어 운영 규칙으로 `Match`까지 만들었다. 실패는 없었다. 처음 적끼리 같은 칸, 보급이 시설 가운데나 처음 적 칸과 겹친 경우, 처음 적이나 보급이 울타리 안에 놓인 경우도 모두 0개였다. 99,476개가 한 번에, 522개가 두 번, 2개가 세 번 만에 만들어졌다. 생성 시간은 평균 0.29ms였다. 10ms 안팎의 최악값은 그 시드를 처음 돌릴 때만 나왔다(시드 5015: 처음 8.8ms, 다시 돌리면 0.43~0.49ms). JIT가 코드를 처음 컴파일하거나 다시 컴파일할 때로 보인다.
- 서버 검사 120/120, 결정론 묶음 23/23.
  - `GeneratorTests`: 시드를 300개에서 1,000개로 늘렸다. 새 검사 `RoomsAndSpots`가 시드마다 운영 방의 `Match`를 만들고, 처음 적과 보급이 울타리 밖에 서로 떨어져 있는지, 배치를 다시 만든 횟수가 최대 횟수의 1/8 안인지 본다. 고정값은 새 맵으로 고쳤고, 시드 1~3과 39의 맵을 글자 그림으로 그려 확인했다.

## 기록과 재생, 버그 제보 — 2026-10-16

결정론 계획의 2단계다. 사용자가 정한 대로 기록은 디스크 파일로 최근 200개 방까지 보관하고, 버그 제보 버튼도 이번에 함께 넣었다.

바꾼 것:

- `Match`의 바깥 요청 메서드(참가·장비·투입·입력·끊김)가 들어온 틱과 받은 값을 스스로 기록하고, 1초(30틱)마다 상태 요약값을 남긴다. `RoomHost`가 `Player`에 직접 넣던 접속 값(끊긴 틱, 첫 접속 대기, 연결 여부)은 `Match.AwaitConnection`·`Match.Connect`로 옮겨 함께 기록한다.
- 기록 파일은 방마다 JSON Lines를 gzip으로 압축한 파일 하나다. 첫 줄은 코드 버전(어셈블리 버전과 커밋)·방 코드·시드·규칙이다. 방 잠금 안에서는 통로에 넣기만 하고, 직렬화와 디스크 쓰기는 따로 도는 작업이 한다. 일반 기록과 제보된 기록을 각각 최근 200개까지 남긴다.
- `MatchReplay`가 기록을 같은 틱에 다시 반영하며 요약값을 비교한다. `tools/Argus.Replay`는 파일 하나·특정 틱에서 멈추기(그 대원의 스냅샷 포함)·폴더 전체 확인을 한다.
- 버그 제보: 화면의 버튼 → `report` → 기록에 틱과 내용 → `reported`(틱). 대원마다 5초에 한 번, 방마다 20개까지 받는다.
- CI: 브라우저 검사가 끝나면 서버를 SIGTERM으로 끄고 남은 기록을 모두 재생한다. 하나라도 갈라지거나 기록이 없으면 실패한다.

확인한 것:

- 서버 검사 새 7개: 60초 진행(대원 넷, 끊김·재접속·장비 변경·거절되는 입력 포함)을 기록대로 다시 돌리면 요약값 60개와 끝 상태가 같다. 입력 하나의 이동 방향을 뒤집으면 바로 다음 요약값에서 멈춘다. 시드가 다르면 첫 요약값에서 멈춘다. 450틱에서 멈추면 그 순간의 상태와 같다. `RoomHost`로 기록한 파일을 읽어 재생하면 끝 상태까지 같고 제보가 틱과 함께 남는다. 보관 정리는 제보된 기록을 남긴다. 끝이 잘린 파일도 남은 부분까지는 재생된다.
- 변조 검사는 처음에 조준을 바꿨는데, 다음 틱의 입력이 조준을 곧바로 덮어써 그 틱에 기술을 쓰지 않으면 상태가 원래대로 돌아왔다. 재생이 틀린 것이 아니라 상태가 실제로 같아진 것이라, 위치 차이가 남는 이동 방향으로 바꿨다.

## 고정 틱과 시드 난수 — 2026-10-16

결정론적 시뮬레이션의 첫 단계다. 코드·규칙·시드가 같은 두 방에 같은 틱마다 같은 입력을 넣으면 같은 상태가 되도록, 진행 시간과 난수를 정했다.

고치기 전 코드에서 두 가지를 측정 프로그램으로 확인했다.

- 시드 73으로 만든 두 방의 처음 적 id가 서로 달랐다(876298303, 4261257). 적 id는 시드와 관계없이 암호 난수로 뽑았다. 운영 방은 시드 없이 모든 난수를 암호 난수로 뽑았다.
- 같은 30초를 0.05초씩 600번 진행한 방과 0.1초씩 300번 진행한 방이 다른 자리에서 끝났다((337.8, 780.4)와 (336.0, 778.0)). 서버는 깨어난 간격을 그대로 `Match.Step(dt)`에 넘겼고, `Step`은 그것을 1/30초 이하 조각으로 나눠 진행했다. 조각 경계가 달라지면 입력이 끊긴 대원을 멈추는 판정 같은 시각 비교가 다른 순간에 일어난다. `Now`도 달랐다(35.10000000000015, 35.10000000000057).

바꾼 것:

- `Match.Step()`은 정확히 한 틱을 진행하고 시간을 받지 않는다. `Now`는 틱 번호에서 바로 구한다. 서버는 `TickClock`으로 지난 시간에 맞는 틱 수를 정해 그만큼 진행하고, 한 틱에 못 미치는 시간은 다음으로 넘긴다. 따라잡기 상한은 0.25초에서 8틱(약 0.27초)으로 바뀌었다.
- 난수는 방마다 32바이트 비밀 시드에서 HMAC-SHA256 카운터 방식으로 뽑는다(`SeededRandom`). 적 id도 같은 생성기에서 뽑는다. 일반 생성기는 공개된 적 id로 내부 상태를 되짚을 수 있어 쓰지 않았다.
- `Match.StateHash()`가 진행 상태 전체를 SHA-256 하나로 요약한다.
- 검사 도우미 `Advance`도 정수 틱으로만 진행한다. 기존 검사 68개는 검사 내용을 고치지 않고 모두 통과했다. `LongStep`은 한 번에 긴 시간을 진행하는 경로가 없어졌으므로, 서버가 가장 많이 밀렸을 때(한 번에 8틱 `StepRoom`)를 확인하도록 바꿨다.

`PeriodicTimer`는 주기를 밀리초 단위로 내려 1/30초 대신 33ms마다 깨어난다. 300번 깨어나는 데 9.898초가 걸렸다. 주석과 `PublishRate` 검사는 33.3ms로 가정하고 있어 바로잡았다. 결론(세 번이 0.1초에 못 미친다)은 같다. 방송 시각을 깨어난 시각에서 잡도록 임시로 되돌리면 고친 검사도 10초에 80번으로 실패한다. 실제 타이머와 `TickClock`을 20초 돌리자 607번 깨어나 15번은 진행할 틱이 없었고 8번은 두 틱이었으며, 진행한 틱은 정확히 600이었다.

## 스냅샷 경량화와 첫 접속 유예 — 2026-10-12

- 방송: `Snapshot.CreateShared`로 팀 공통 부분을 한 번만 만들고, 수신자마다 `Snapshot.Personalize`로 `you`와 보급 `cooldown`만 덮어쓴다. 이전에는 수신자마다 시야 계산과 가시성 필터까지 전부 새로 했다. 바꾸기 전에 같은 틱의 네 스냅샷이 `you`와 보급 `cooldown` 외에는 바이트 단위로 같다는 것을 실측으로 확인했다.
- 시야 다각형 좌표를 정수로 보낸다. 서버에서도 `int[]`로 들고 있어 직렬화가 빠르다. 그리기 전용이라 1단위 미만은 화면에서 구분되지 않는다.
- WebSocket permessage-deflate 압축을 켰다. 협상 방식이라 지원하지 않는 클라이언트도 그대로 접속한다.
- HTTP 참가 후 한 번도 접속하지 않은 자리는 15초(`Rules.FirstConnectSeconds`) 뒤에 풀린다. 접속했다가 끊긴 대원의 120초 복구 유예는 그대로다.

측정 환경은 Linux/WSL, .NET SDK 10.0.112, Node.js 24.15.0이며 모두 4명이 살아 있는 상태다.

| 항목 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 스냅샷 JSON, 캠프에 정지 | 10,548 B | 8,549 B |
| 실제 전송, 캠프에 정지 | 10,548 B (압축 없음) | 116 B |
| 실제 전송, 계속 이동 | — | 1,405 B (JSON 8,721 B의 16%) |
| 방 하나 송신량 | 412 KiB/s | 계속 이동 시 55 KiB/s |
| 방송 1회 CPU (만들기 + 직렬화) | 약 480 µs | 약 170~190 µs |
| 방송 1회 압축 CPU | 없음 | 약 810 µs |

- 실제 전송량은 서버 앞에 바이트를 세는 TCP 프록시를 두고 Node.js WebSocket으로 쟀다. 협상 결과는 `permessage-deflate; client_max_window_bits=15`였다.
- CPU는 서버 프로젝트를 참조하는 임시 콘솔 프로그램에서 Release로 3,000회 반복해 쟀다. 변경 전 값은 수신자마다 `Snapshot.Create`를 부르고 시야를 `double`로 담던 방식이다. 압축 CPU는 서버와 같은 zlib 기본 수준으로 문맥을 유지하며 메시지마다 동기 플러시해 쟀다. 이 방식으로 계산한 압축률(14%)이 실제 전송 측정(16%)과 맞았다.
- **압축은 CPU를 더 쓴다.** 만들기·직렬화에서 줄인 시간보다 압축 비용이 커서, 방송 1회의 총 CPU는 약 480 µs에서 약 1 ms로 늘었다. 대신 송신량이 약 7.5배 줄었다. 집에서 서버를 띄우면 업로드 대역폭이, 클라우드에서는 송신 비용이 먼저 부족해지므로 압축을 켜는 쪽을 택했다. 방 32개를 모두 채우면 압축에만 CPU 코어 하나의 약 26%를 쓴다고 추정한다.
- 변경 전 송신량은 캠프에 정지한 상태로 쟀다. 압축이 없을 때는 이동 여부가 JSON 크기에 거의 영향을 주지 않는다.

## 질문 정리 반영 — 2026-10-12

코드 리뷰에서 모은 질문에 대한 결정을 반영했다. 수치 조정이 아니라 동작 변경과 문서 정리다.

이 환경의 소프트웨어 WebGL로 여러 화면을 동시에 렌더링할 때 초기화 지연이 발생했다. 최종 통합 검사는 Chromium의 WebGL을 비활성화해 실제 제품에 포함된 Canvas 대체 경로를 사용했다. 하드웨어 WebGL의 다중 클라이언트 성능, 적 180마리의 프레임 유지, 최대 방 수의 서버 부하는 별도 측정이 필요하다.

Docker Desktop의 WSL 연동이 없어 Docker 이미지 빌드는 실행하지 못했다. GKE를 포함한 클라우드 배포는 수행하지 않았다. 프로토타입은 메모리 기반 단일 프로세스이며 서버 재시작 시 진행 중인 작전이 사라진다.
