## 보류했던 리뷰 지적 4건 반영 — 2026-10-14

이유를 적어 보류했던 1차 리뷰 7번과 재리뷰 5·6·9번을 모두 고쳤다. 찾은 문제는 다음 작업으로 미루지 않기로 했다.

**기술 동작 속성화(재리뷰 5번).** 판정 코드의 `Skill.Id == "parry"`·`"grab"`·`"strike"` 비교 7곳을 `SkillDefinition`의 `GuardsFront`·`HasFollowup`·`SingleTarget`·`BreaksStructures`로 바꿨다. 클라이언트의 방어 호와 반격 그림도 `rules.skills`의 같은 속성을 쓴다. 검사 `SkillFlags`는 id만 다른 기술 세 개(shield, hook, smash)로 네 동작을 확인한다. 처음 쓴 검사는 정면 타격만 막아 봤는데, id로 판정해도 `Kind`가 방어라서 그대로 이겨 문제를 잡지 못했다. 그래서 조준에서 40° 벗어난 타격 방어, 방어 중 무행동 적 공격 안 함, 반격, 단일 대상, 시설 파괴를 각각 확인하도록 다시 썼다. 판정 지점 다섯 곳을 하나씩 id 비교로 되돌리면 매번 실패한다.

**적 조향(1차 리뷰 7번).** 직진 → 흐름장 → 양옆 두 번을 차례로 시도하던 이동을 조향으로 바꿨다. 움직이기 전에 몸이 직선으로 지나갈 수 있는지(몸 중심선과 양옆 두 선)를 보고 직진·흐름장을 고른 뒤, 이웃 적과의 분리 방향을 더해 `MoveBody`를 한 번만 부른다. 2026-10-12에는 지형을 만들기 어렵다고 적었던 모서리 끼임 회귀 검사 `CornerSlip`을 만들었다. 벽 타일 (32,10)–(32,11)의 아래쪽 면을 12만큼 스치는 직선이며, D-3 이전 방식과 몸 통과 판단을 뺀 방식에서 모두 "모서리에 걸려 멈췄습니다"로 실패한다.

| 적 60마리 밀집(행동 없이 계속 밀고 들어옴), 3회 | 예전 | 조향 |
| --- | --- | --- |

분리 방향 때문에 적이 덜 빽빽하게 뭉친다. 실제 임무에서는 적이 75 안에 들면 행동하며 멈추므로 영향이 작다고 보며, 임무 완료 브라우저 검사는 그대로 통과했다.

**바뀌지 않는 정보 전송(재리뷰 6번), protocol v3.** `walls`는 그 연결이 아직 받지 못한 판일 때만, `rules`·`map`은 아직 받지 못했을 때만 담는다. 받았는지는 만들 때가 아니라 실제로 보낸 뒤 `Peer.MarkSent`가 기록한다. 연결마다 쌓인 메시지는 느린 수신자에서 버려질 수 있어서, 만들 때 기록하면 바뀐 벽이 영영 전달되지 않을 수 있기 때문이다. 검사 `StaticParts`는 보내기 전에는 다시 담는지, 보낸 뒤에는 빼는지, 벽이 바뀌면 벽만 다시 담는지를 확인한다. 넣자마자 보냈다고 기록하도록 바꾸면 실패한다. 통신 형식이 바뀌어 protocol v3로 올렸다. 클라이언트와 임무 검사 봇은 빠진 값을 같은 방의 이전 스냅샷으로 채운다.

**라벨 재사용(재리뷰 9번).** 쓰지 않게 된 라벨을 바로 해제하지 않고 숨겨 두었다가 다시 쓴다. 숨겨 두는 수는 64개까지이고 넘는 것은 해제한다. 2026-10-07의 누수 검사는 "모두 파괴된다" 대신 "같은 객체를 다시 쓰고 숨겨 둔 수가 64를 넘지 않는다"로 바꿨다. 상한을 없애면 실패한다(200개가 남음). 시야를 벗어난 적의 예고 라벨 검사는 "파괴" 대신 "목록에서 빠지고 화면에서 숨겨짐"을 확인한다.

측정은 페이지 시계를 직접 넘기는 결정적 시뮬레이션으로 했다. 서버는 입력을 50ms 뒤에 받아 30Hz로 적용하고, 스냅샷을 10Hz로 50ms 늦게 보낸다(왕복 100ms). 오른쪽으로 계속 이동하며 1~2.5초 구간에서 "입력대로라면 있어야 할 위치"와 그려진 위치의 차이를 쟀다. 같은 시뮬레이션을 예전 목표 계산으로도 돌렸다.

| 방식 | 평균 | 최소 | 최대 |
| --- | --- | --- | --- |
| 예전 (서버 위치 + 현재 입력 × 수신 후 경과) | 16.2 | 14.9 | 21.0 |
| 서버 재조정 | 1.3 | 0.0 | 6.1 |

단위는 월드 단위이며 플레이어 지름은 26이다. 예전 방식은 속도 × 왕복 지연(180 × 0.1 = 18) 근처에 머물렀고, 재조정 뒤에는 입력 하나가 유지되는 시간(1/30초, 6단위) 안쪽이다.

검사:

측정하지 않은 것:

## 스냅샷 경량화와 첫 접속 유예 — 2026-10-12

- 방송: `Snapshot.CreateShared`로 팀 공통 부분을 한 번만 만들고, 수신자마다 `Snapshot.Personalize`로 `you`와 보급 `cooldown`만 덮어쓴다. 이전에는 수신자마다 시야 계산과 가시성 필터까지 전부 새로 했다. 바꾸기 전에 같은 틱의 네 스냅샷이 `you`와 보급 `cooldown` 외에는 바이트 단위로 같다는 것을 실측으로 확인했다.
- 시야 다각형 좌표를 정수로 보낸다. 서버에서도 `int[]`로 들고 있어 직렬화가 빠르다. 그리기 전용이라 1단위 미만은 화면에서 구분되지 않는다.
- WebSocket permessage-deflate 압축을 켰다. 협상 방식이라 지원하지 않는 클라이언트도 그대로 접속한다.
- HTTP 참가 후 한 번도 접속하지 않은 자리는 15초(`Rules.FirstConnectSeconds`) 뒤에 풀린다. 접속했다가 끊긴 대원의 120초 복구 유예는 그대로다.

측정 환경은 Linux/WSL, .NET SDK 10.0.112, Node.js 24.15.0이며 모두 4명이 살아 있는 상태다.

| 항목 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 스냅샷 JSON, 캠프에 정지 | 10,548 B | 8,549 B |
| 실제 전송, 캠프에 정지 | 10,548 B (압축 없음) | 116 B |
| 실제 전송, 계속 이동 | — | 1,405 B (JSON 8,721 B의 16%) |
| 방 하나 송신량 | 412 KiB/s | 계속 이동 시 55 KiB/s |
| 방송 1회 CPU (만들기 + 직렬화) | 약 480 µs | 약 170~190 µs |
| 방송 1회 압축 CPU | 없음 | 약 810 µs |

- 실제 전송량은 서버 앞에 바이트를 세는 TCP 프록시를 두고 Node.js WebSocket으로 쟀다. 협상 결과는 `permessage-deflate; client_max_window_bits=15`였다.
- CPU는 서버 프로젝트를 참조하는 임시 콘솔 프로그램에서 Release로 3,000회 반복해 쟀다. 변경 전 값은 수신자마다 `Snapshot.Create`를 부르고 시야를 `double`로 담던 방식이다. 압축 CPU는 서버와 같은 zlib 기본 수준으로 문맥을 유지하며 메시지마다 동기 플러시해 쟀다. 이 방식으로 계산한 압축률(14%)이 실제 전송 측정(16%)과 맞았다.
- **압축은 CPU를 더 쓴다.** 만들기·직렬화에서 줄인 시간보다 압축 비용이 커서, 방송 1회의 총 CPU는 약 480 µs에서 약 1 ms로 늘었다. 대신 송신량이 약 7.5배 줄었다. 집에서 서버를 띄우면 업로드 대역폭이, 클라우드에서는 송신 비용이 먼저 부족해지므로 압축을 켜는 쪽을 택했다. 방 32개를 모두 채우면 압축에만 CPU 코어 하나의 약 26%를 쓴다고 추정한다.
- 변경 전 송신량은 캠프에 정지한 상태로 쟀다. 압축이 없을 때는 이동 여부가 JSON 크기에 거의 영향을 주지 않는다.

검사:

- 서버 검사 **41/41 통과**. 공유 메시지를 다음 수신자에게 재사용해도 앞 수신자의 보급 대기 시간이 남지 않고 따로 만든 스냅샷과 같은지, 전송되는 시야 좌표가 정수인지 확인하는 검사를 추가했다. 한 번도 접속하지 않은 자리는 15초 뒤에 풀리지만 끊긴 대원은 같은 시간이 지나도 남는지 확인하는 검사도 추가했다. 덮어쓰기와 첫 접속 표시를 각각 임시로 망가뜨리면 두 검사가 실패하는 것을 확인했다.

## 질문 정리 반영 — 2026-10-12

코드 리뷰에서 모은 질문에 대한 결정을 반영했다. 수치 조정이 아니라 동작 변경과 문서 정리다.

- 저장소: `.idea` 10개 파일을 추적에서 빼고 `.gitignore`에 `.idea/`를, `.gitattributes`에 `* text=auto eol=lf`를 넣었다. 저장소가 `/mnt/e`에 있어 Windows IDE가 CRLF로 다시 쓰면서 8개 파일이 더티로 남아 있었다. `diff.external = difft` 설정 때문에 `git diff`가 "No changes"로 보여 원인이 드러나지 않았다.
- 입력: 동시에 눌린 슬롯 중 마지막에 누른 것이 나간다. 이전에는 체인 if 때문에 Q(4) > Space(3) > 우클릭(2) > 좌클릭(1)로 우선순위가 고정이었다. 자동 반복은 누름 순서를 바꾸지 않는다.
- 적 생성: 분대 시야 안에서는 생성하지 않는다. 벽·몸에 막히거나 보이는 자리면 각도를 최대 12번 다시 뽑고, 끝까지 자리가 없으면 그 회차를 넘긴다. 이전에는 한 번 뽑아 실패하면 조용히 넘어가 실효 생성 간격이 설정값보다 길었다.
- 적 이동: 사선이 열려 있어도 몸이 모서리에 걸리면 흐름장 경로로 돌아간다. 그래도 막히면 양옆을 모두 시도한다. 이전에는 `Id % 2`로 정한 한쪽만 한 번 시도했다. 전진 판정에 못 미치는 미세한 이동 결과는 그대로 남긴다.
- 방 진행: 방이 둘 이상이면 `Parallel.For`로 동시에 진행한다. 방마다 상태와 `lock`이 독립이라 가능하다. 방이 하나면 작업 분배 없이 직접 호출한다.

측정하지 않은 것:

임무·자원·통신 검사는 네 슬롯 검증, 빈 마나의 사용 거절, 빗나감 비용, 입력 폭주에 의한 중복 사용 방지, 마나 자연 회복 없음, 개인별 보급, 최초·난입·증원 5초와 마나 0, 전멸 우선, 전역 피해, 숨겨진 적·기술·효과의 직렬화 제외, 재접속 상태 유지와 만료를 포함한다. 투입 위치 선택 단계에서 숨겨진 적 점유 여부를 드러내지 않고 실제 도착 때 몸 겹침을 막는 경우도 검사한다.

브라우저 검사는 네 탭의 참가·투입·보급·기술 중 이동·새로고침 복구, 네 슬롯 입력과 자유 슬롯 저장, 잘못된 토큰·위조 자원·재전송·잘못된 슬롯·정원 제한·난입·같은 토큰 연결 교체를 확인한다. 렌더러는 적 120개 교체 후 라벨과 Pixi 객체가 쌓이지 않는지, 방 변경 정리, 예고 색상 변경과 시야 이탈 시 제거, 적 몸 충돌과 아군 겹침을 확인한다.

실제 임무 검사는 공개 HTTP 참가와 WebSocket 입력만 사용한 네 대원이 보급 후 함께 이동하며 적의 예고에 대응하고, 시설 세 곳을 파괴하고, 탈출 구역을 20초 확보해 성공하는 것을 확인했다. 마지막 전체 실행에서 이 검사는 약 35초 걸렸다. 서버 상태 변경용 HTTP API나 테스트용 순간이동·자원 충전은 사용하지 않는다. 단위 검사의 직접 상태 설정과 구분한다. 이 자동화 분대의 완료 시간은 사람의 평균 임무 시간이나 재미·난이도 측정이 아니다.

검증 중 발견해 수정한 사항:

- 벽을 5단위마다 샘플링하던 사선 검사가 짧은 모서리 교차를 놓쳤다. 정확한 타일 경계 순회로 바꾸고 `(464, 498)` 부근의 양 끝이 비어 있는 벽 차단 사례를 검사했다.
- 연결 교체 때 종료 프레임 직후 수신 취소가 소켓을 중단해 4001 대신 1006이 보였다. 종료 응답을 기다린 뒤 정리하도록 고쳤고 실제 소켓 검사에서 4001을 확인했다.
- 투입 요청이 적 점유 여부를 즉시 검사하면 숨겨진 적의 존재를 좌표별 요청으로 탐색할 수 있었다. 선택 단계는 공개된 벽만 검사하고, 적과의 겹침은 5초 뒤 실제 도착 시 검사하도록 바꿨다.

브라우저는 WebGL을 비활성화한 Chromium에서 제품의 Canvas 대체 경로를 사용했다. 하드웨어 WebGL, 최대 방 32개·적 60마리의 부하, 장시간 힙 메모리, 사람의 조작감과 장비 밸런스는 측정하지 않았다. Docker/GKE 배포도 이번 작업 범위에 없다. 받아치기 후속 반격과 잡기 예고의 관계에는 확인 중인 해석이 있으며 [전투 명세](combat.md)에 현재 처리를 명시했다.

재현 명령:

```bash
dotnet run --project tests/Argus.Server.Tests
npm --prefix client run build
dotnet run --project server/Argus.Server --urls http://127.0.0.1:5088
# 서버 실행 상태에서 별도 터미널
cd client
ARGUS_URL=http://127.0.0.1:5088 npm run test:e2e
```

이 작업 환경에서는 Playwright 브라우저와 Linux 라이브러리를 `/tmp/argus-playwright`, `/tmp/argus-browser-deps`에 따로 설치해 `PLAYWRIGHT_BROWSERS_PATH`, `LD_LIBRARY_PATH`, `FONTCONFIG_FILE`을 지정했다. 일반 환경에서는 README의 `playwright install --with-deps chromium` 절차를 사용할 수 있다.
