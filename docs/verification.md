## 고정 틱과 시드 난수 — 2026-10-16

결정론적 시뮬레이션의 첫 단계다. 코드·규칙·시드가 같은 두 방에 같은 틱마다 같은 입력을 넣으면 같은 상태가 되도록, 진행 시간과 난수를 정했다.

고치기 전 코드에서 두 가지를 측정 프로그램으로 확인했다.

- 시드 73으로 만든 두 방의 처음 적 id가 서로 달랐다(876298303, 4261257). 적 id는 시드와 관계없이 암호 난수로 뽑았다. 운영 방은 시드 없이 모든 난수를 암호 난수로 뽑았다.
- 같은 30초를 0.05초씩 600번 진행한 방과 0.1초씩 300번 진행한 방이 다른 자리에서 끝났다((337.8, 780.4)와 (336.0, 778.0)). 서버는 깨어난 간격을 그대로 `Match.Step(dt)`에 넘겼고, `Step`은 그것을 1/30초 이하 조각으로 나눠 진행했다. 조각 경계가 달라지면 입력이 끊긴 대원을 멈추는 판정 같은 시각 비교가 다른 순간에 일어난다. `Now`도 달랐다(35.10000000000015, 35.10000000000057).

바꾼 것:

- `Match.Step()`은 정확히 한 틱을 진행하고 시간을 받지 않는다. `Now`는 틱 번호에서 바로 구한다. 서버는 `TickClock`으로 지난 시간에 맞는 틱 수를 정해 그만큼 진행하고, 한 틱에 못 미치는 시간은 다음으로 넘긴다. 따라잡기 상한은 0.25초에서 8틱(약 0.27초)으로 바뀌었다.
- 난수는 방마다 32바이트 비밀 시드에서 HMAC-SHA256 카운터 방식으로 뽑는다(`SeededRandom`). 적 id도 같은 생성기에서 뽑는다. 일반 생성기는 공개된 적 id로 내부 상태를 되짚을 수 있어 쓰지 않았다.
- `Match.StateHash()`가 진행 상태 전체를 SHA-256 하나로 요약한다.
- 검사 도우미 `Advance`도 정수 틱으로만 진행한다. 기존 검사 68개는 검사 내용을 고치지 않고 모두 통과했다. `LongStep`은 한 번에 긴 시간을 진행하는 경로가 없어졌으므로, 서버가 가장 많이 밀렸을 때(한 번에 8틱 `StepRoom`)를 확인하도록 바꿨다.

`PeriodicTimer`는 주기를 밀리초 단위로 내려 1/30초 대신 33ms마다 깨어난다. 300번 깨어나는 데 9.898초가 걸렸다. 주석과 `PublishRate` 검사는 33.3ms로 가정하고 있어 바로잡았다. 결론(세 번이 0.1초에 못 미친다)은 같다. 방송 시각을 깨어난 시각에서 잡도록 임시로 되돌리면 고친 검사도 10초에 80번으로 실패한다. 실제 타이머와 `TickClock`을 20초 돌리자 607번 깨어나 15번은 진행할 틱이 없었고 8번은 두 틱이었으며, 진행한 틱은 정확히 600이었다.

새 검사 5개:

| 검사 | 확인하는 것 |
| --- | --- |
| `SeededSequence` | 생성기의 첫 값 5개가 서버 코드와 따로 파이썬 `hmac`으로 계산한 값과 같음. 같은 시드는 같은 순서, 다른 시드는 다른 값, 범위 안의 값 |
| `SameSeedEnemies` | 시드가 같으면 처음 적 id와 상태 요약이 같고, 시드가 다르면 다름 |
| `SameSeedSameRun` | 대원 둘이 90초 동안 기술을 쓰며 싸우는 각본(적 29마리, 엘리트 포함, 처치 17, 사망 2)을 두 번 돌리면 2,700틱 모두 상태 요약이 같음. 한 틱의 조준만 0.001 바꾸면 바로 그 틱부터 다름 |
| `TickBatching` | 1틱씩 12번 진행한 방과 1·2·3·6틱으로 나눠 진행한 방이 같음 |
| `TickClockWakes` | 불규칙하게 깨어나도 지난 시간만큼의 틱을 빠짐없이 진행하고, 5초 멈춘 뒤에는 8틱만 진행함 |

적 id를 예전처럼 암호 난수로 뽑게 임시로 되돌리면 `SameSeedEnemies`, `SameSeedSameRun`, `TickBatching`이 실패한다.

아직 남은 것: 진행 계산은 `float` 벡터와 `Math.Sin`·`Cos`·`Atan2`·`Pow`를 쓴다. 같은 기계에서는 결과가 같지만 운영체제나 CPU가 다르면 수학 함수 결과의 마지막 자리가 달라질 수 있어, 기계가 달라도 같다는 보장은 아직 없다. 입력이 도착한 틱도 기록하지 않는다.

따로 발견한 것: 처음 배치하는 적 셋 가운데 (970, 570)의 적은 장애물 칸 (20, 11) 안에 놓여 생성되지 않는다. 그 장애물은 적 배치가 들어온 10월 11일보다 먼저 있었으므로 처음부터 적은 둘이었다. 엘리트 작전에서는 분쇄자가 처음에 나오지 않는다. 게임 내용을 바꾸는 일이라 이 작업에서는 고치지 않았다.

검사: 서버 검사 **73/73**, 브라우저 검사 16/16(화면 검사 7개 포함), TypeScript 검사와 프로덕션 빌드 통과.

## 원호 앞의 긴 선 — 2026-10-16

적이 행동을 예고할 때 화면 왼쪽 위에서 적 쪽으로 긴 선이 그어진다는 제보를 받았다(사용자 화면). 원인은 PixiJS 8.22의 경로 처리였다. `fill`·`stroke` 뒤에는 다음 경로가 직전 경로의 마지막 점에서 시작한다(`GraphicsContext._initNextPathLocation`). 그런데 `GraphicsPath.getLastPoint`는 직전 경로가 원·사각형·다각형 같은 도형으로 끝나면 마지막 점을 계산하지 않는다. 그 대신 넘겨받은 임시 점(`Point.shared`)을 그대로 돌려준다. `Point.shared`는 읽을 때마다 0으로 되돌리는 getter이므로(`Point.mjs` 191행), 다음 경로는 늘 원점(0, 0)에서 시작한다. 그 뒤에 그린 원호는 원점에서부터 직선으로 이어진다.

같은 이유로 세 곳에서 선이 생겼다. 적 예고 게이지는 예고 범위 다각형 뒤, 받아치기 방어 호는 그 전에 그린 적이나 다른 대원의 도형 뒤, 탈출 진행도는 탈출 구역 원 뒤다.

원호는 `arcOnNewPath` 하나로만 그린다. 이 함수는 `beginPath()`로 새 경로를 연 뒤 원호를 그리고, 이유도 이 함수에만 적었다. 화면 검사는 실제 `World`가 그린 결과에서 기대하는 원호 세 개를 반지름과 중심으로 찾고, 그 앞에 다른 점이 붙지 않았는지 확인한다. 기대하는 원호를 찾지 못하면 실패하므로, Pixi의 내부 구조가 바뀌어 검사가 아무것도 보지 못할 때도 조용히 통과하지 않는다. 고치기 전 코드에서는 세 원호 모두 앞에 `moveTo 0,0`이 붙어 실패했다. 같은 장면을 찍어, 고치기 전에는 왼쪽 위에서 적의 게이지까지 선이 그어지고 고친 뒤에는 사라지는 것도 눈으로 확인했다.

PR #2 리뷰를 받아 고쳤다. 처음에는 원인을 "다각형 뒤"로만 적었고, 원호마다 `beginPath()`를 따로 붙였으며, 검사가 원호 개수를 3으로 못 박았다. 리뷰는 시작점이 `Point.shared`에 남은 임의의 좌표라고 보았지만, 8.22의 getter는 읽을 때마다 0으로 되돌리므로 시작점은 원점으로 정해져 있다.

검사: 화면 검사 7/7, 브라우저 검사 16/16, TypeScript 검사와 프로덕션 빌드 통과.

## 서버 재조정 — 2026-10-13

- 공식 클라이언트에 서버 재조정을 넣었다. `main.ts`의 `sendInput`이 실제로 보낸 입력을 순번과 함께 `World.recordInput`으로 기록하고, 스냅샷이 오면 `ack` 이하의 입력을 버린다. 그릴 때마다 서버 위치에서 출발해 남은 입력을 보낸 순서대로 다시 적용한 곳을 보정 목표로 삼는다. 각 입력은 다음 입력을 보낼 때까지(마지막 입력은 지금까지) 움직이며, 서버의 입력 만료와 맞춰 한 입력당 0.35초로 자른다.

측정은 페이지 시계를 직접 넘기는 결정적 시뮬레이션으로 했다. 서버는 입력을 50ms 뒤에 받아 30Hz로 적용하고, 스냅샷을 10Hz로 50ms 늦게 보낸다(왕복 100ms). 오른쪽으로 계속 이동하며 1~2.5초 구간에서 "입력대로라면 있어야 할 위치"와 그려진 위치의 차이를 쟀다. 같은 시뮬레이션을 예전 목표 계산으로도 돌렸다.

| 방식 | 평균 | 최소 | 최대 |
| --- | --- | --- | --- |
| 예전 (서버 위치 + 현재 입력 × 수신 후 경과) | 16.2 | 14.9 | 21.0 |
| 서버 재조정 | 1.3 | 0.0 | 6.1 |

단위는 월드 단위이며 플레이어 지름은 26이다. 예전 방식은 속도 × 왕복 지연(180 × 0.1 = 18) 근처에 머물렀고, 재조정 뒤에는 입력 하나가 유지되는 시간(1/30초, 6단위) 안쪽이다.

## 스냅샷 경량화와 첫 접속 유예 — 2026-10-12

- 방송: `Snapshot.CreateShared`로 팀 공통 부분을 한 번만 만들고, 수신자마다 `Snapshot.Personalize`로 `you`와 보급 `cooldown`만 덮어쓴다. 이전에는 수신자마다 시야 계산과 가시성 필터까지 전부 새로 했다. 바꾸기 전에 같은 틱의 네 스냅샷이 `you`와 보급 `cooldown` 외에는 바이트 단위로 같다는 것을 실측으로 확인했다.
- 시야 다각형 좌표를 정수로 보낸다. 서버에서도 `int[]`로 들고 있어 직렬화가 빠르다. 그리기 전용이라 1단위 미만은 화면에서 구분되지 않는다.
- WebSocket permessage-deflate 압축을 켰다. 협상 방식이라 지원하지 않는 클라이언트도 그대로 접속한다.
- HTTP 참가 후 한 번도 접속하지 않은 자리는 15초(`Rules.FirstConnectSeconds`) 뒤에 풀린다. 접속했다가 끊긴 대원의 120초 복구 유예는 그대로다.

측정 환경은 Linux/WSL, .NET SDK 10.0.112, Node.js 24.15.0이며 모두 4명이 살아 있는 상태다.

| 항목 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 스냅샷 JSON, 캠프에 정지 | 10,548 B | 8,549 B |
| 실제 전송, 캠프에 정지 | 10,548 B (압축 없음) | 116 B |
| 실제 전송, 계속 이동 | — | 1,405 B (JSON 8,721 B의 16%) |
| 방 하나 송신량 | 412 KiB/s | 계속 이동 시 55 KiB/s |
| 방송 1회 CPU (만들기 + 직렬화) | 약 480 µs | 약 170~190 µs |
| 방송 1회 압축 CPU | 없음 | 약 810 µs |

- 실제 전송량은 서버 앞에 바이트를 세는 TCP 프록시를 두고 Node.js WebSocket으로 쟀다. 협상 결과는 `permessage-deflate; client_max_window_bits=15`였다.
- CPU는 서버 프로젝트를 참조하는 임시 콘솔 프로그램에서 Release로 3,000회 반복해 쟀다. 변경 전 값은 수신자마다 `Snapshot.Create`를 부르고 시야를 `double`로 담던 방식이다. 압축 CPU는 서버와 같은 zlib 기본 수준으로 문맥을 유지하며 메시지마다 동기 플러시해 쟀다. 이 방식으로 계산한 압축률(14%)이 실제 전송 측정(16%)과 맞았다.
- **압축은 CPU를 더 쓴다.** 만들기·직렬화에서 줄인 시간보다 압축 비용이 커서, 방송 1회의 총 CPU는 약 480 µs에서 약 1 ms로 늘었다. 대신 송신량이 약 7.5배 줄었다. 집에서 서버를 띄우면 업로드 대역폭이, 클라우드에서는 송신 비용이 먼저 부족해지므로 압축을 켜는 쪽을 택했다. 방 32개를 모두 채우면 압축에만 CPU 코어 하나의 약 26%를 쓴다고 추정한다.
- 변경 전 송신량은 캠프에 정지한 상태로 쟀다. 압축이 없을 때는 이동 여부가 JSON 크기에 거의 영향을 주지 않는다.

## 질문 정리 반영 — 2026-10-12

코드 리뷰에서 모은 질문에 대한 결정을 반영했다. 수치 조정이 아니라 동작 변경과 문서 정리다.

- 저장소: `.idea` 10개 파일을 추적에서 빼고 `.gitignore`에 `.idea/`를, `.gitattributes`에 `* text=auto eol=lf`를 넣었다. 저장소가 `/mnt/e`에 있어 Windows IDE가 CRLF로 다시 쓰면서 8개 파일이 더티로 남아 있었다. `diff.external = difft` 설정 때문에 `git diff`가 "No changes"로 보여 원인이 드러나지 않았다.
- 입력: 동시에 눌린 슬롯 중 마지막에 누른 것이 나간다. 이전에는 체인 if 때문에 Q(4) > Space(3) > 우클릭(2) > 좌클릭(1)로 우선순위가 고정이었다. 자동 반복은 누름 순서를 바꾸지 않는다.
- 적 생성: 분대 시야 안에서는 생성하지 않는다. 벽·몸에 막히거나 보이는 자리면 각도를 최대 12번 다시 뽑고, 끝까지 자리가 없으면 그 회차를 넘긴다. 이전에는 한 번 뽑아 실패하면 조용히 넘어가 실효 생성 간격이 설정값보다 길었다.
- 적 이동: 사선이 열려 있어도 몸이 모서리에 걸리면 흐름장 경로로 돌아간다. 그래도 막히면 양옆을 모두 시도한다. 이전에는 `Id % 2`로 정한 한쪽만 한 번 시도했다. 전진 판정에 못 미치는 미세한 이동 결과는 그대로 남긴다.
- 방 진행: 방이 둘 이상이면 `Parallel.For`로 동시에 진행한다. 방마다 상태와 `lock`이 독립이라 가능하다. 방이 하나면 작업 분배 없이 직접 호출한다.

## 포탑 라벨과 설치 미리보기 수정 검증 — 2026-10-07

수정 전 실제 World/Pixi 객체를 사용하는 브라우저 검사에서 두 문제를 재현했다. 포탑 120개를 순차 교체하자 기본 라벨 3개를 포함해 123개가 남았다. `(464, 498)`에서 313°를 조준하면 설치 지점 자체는 비어 있어도 두 점 사이의 벽을 통과하므로 서버는 거부했지만 미리보기는 초록색 `G`를 표시했다.

사용하지 않는 라벨은 매 프레임 끝에 캐시와 Pixi 컨테이너에서 제거하고 객체·스타일을 해제한다. 미리보기에는 서버의 `BattleMap.RayWall`과 같은 간격의 벽 차단 검사를 추가했다. 기존 라벨의 표시 색상도 갱신한다.

- 클라이언트 TypeScript 검사와 프로덕션 빌드 통과.
- 서버 검사 **24/24 통과**. 모서리 사례에서 설치 거절 후 벽 파괴 시 설치 성공을 확인하는 검사를 추가했다.
- 브라우저 검사 **6/6 통과**: 기존 통합 검사 4개와 새 렌더러 검사 2개를 각각 실행했다.
- 새 검사는 120개 교체 후 현재 라벨만 남는지, 제거한 포탑과 이전 방 대원의 라벨이 해제되는지, 미리보기의 가능·불가 문구와 색상, 벽 파괴 후 가능 표시 복귀를 확인한다.

브라우저 검사는 앞선 검증과 같은 Canvas 대체 경로를 사용했다. 라벨 수와 객체 해제를 검사했으며 장시간 힙 메모리 사용량을 측정한 것은 아니다.
